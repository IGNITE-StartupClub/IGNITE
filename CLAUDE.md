# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev        # Start dev server at localhost:4321
npm run build      # Build for production
npm run preview    # Preview the production build
npm test           # Unit tests (node --test, needs Node >= 22.18 for TypeScript)
```

Tests use Node's built-in runner on `src/**/*.test.ts`; only modules without extensionless local imports can be tested this way. There is no lint script — ESLint and Prettier are configured but must be run manually (`npx eslint .` / `npx prettier --write .`); ESLint currently fails, see "ESLint" under Project rules.

## Architecture

This is an **Astro 5 site** with **server-side rendering** (output: 'server') deployed to **Vercel**. It uses React for interactive components, Tailwind CSS + SCSS for styling, and MDX for content pages.

### Key architectural layers

**Content (`src/data/`)** — All static, editable website content lives here, not in components:
- `staticContent.ts` — Hero text, FAQs, Features, Navigation, Footer, and global config
- `teamsData.ts` — Team member data (name, position, photo, bio)
- `eventsData.ts` / `questionnaireConfig.ts` / `kpiData.ts` — Domain-specific data

**Email Templates (`src/templates/emails/`)** — HTML email templates are fully separated from API logic. Each file exports a subject function and an HTML function. Edit email copy here, not in API routes.

**API Routes (`src/pages/api/`)** — Server endpoints that handle:
- `submit.ts` — Membership application form: validates input, encrypts all fields with AES-256-GCM, stores encrypted data in **MongoDB**, sends the team notification and the applicant confirmation (which carries the WhatsApp link) via **Resend**
- `contact.ts` — Contact form, sends emails via Resend
- `community.ts` — Community signup (Community page and footer): validates the address, mails the WhatsApp invite link, no confirmation step. A Mongo TTL collection `community_invites` allows one invite per address and 24 hours (409 on repeat).
- `members/` — Members area: `login.ts` checks email and password and sets the session cookie, `code.ts` mails a one-time code to set a password, `password.ts` sets it with that code, `admin.ts` is the member management for admins, `profile.ts` saves name and team from the team choice, `logout.ts` ends the session
- `mcp.ts`, `oauth/`, `calendar/` — AI assistants and calendar subscription, see "Connections" under Project rules
- `cron/` — Scheduled jobs from `vercel.json` (health check, database report, monthly applicants, task digest, nightly task archive, morning error report). Each starts with `rejectCron(request)` (`src/lib/cron.ts`), which answers 401 unless the request carries `Authorization: Bearer <CRON_SECRET>`; without `CRON_SECRET` every cron request is refused.

**Content Collections (`src/content/`)** — Markdown-based collections for `events` and `projects`, defined in `src/content.config.mjs`. New content files go in the respective subdirectories.

**Components** — `.astro` components for layout/structural UI; `.jsx` components (React) for interactive features (forms, search, 3D effects, animations). The `LiquidEther`, `Orb`, `SplitText`, and `stakeholder-map` subdirectories contain complex visual/interactive components.

**Layouts (`src/layouts/`)** — `DefaultLayout.astro` wraps all pages; provides SEO meta, fonts, Plausible analytics, and the global animated background dots.

### Path alias

`@` maps to `/src` (configured in `astro.config.mjs` and Vite).

### Required environment variables

The application will throw at startup if any of these are missing:

| Variable | Purpose |
|---|---|
| `RESEND_API_KEY` | All emails: application, contact, community invite, reports |
| `MONGODB_URI` | MongoDB connection string |
| `MONGODB_DB` | MongoDB database name |
| `ENCRYPTION_SECRET` | 32-byte hex key for AES-256-GCM encryption of applicant data |
| `EMAIL_RECIPIENT_1` | Primary admin email recipient |
| `EMAIL_RECIPIENT_2` | (Optional) Secondary admin email recipient |
| `SITE_URL` | (Optional) Public URL, shown in the database report |
| `CRON_SECRET` | Secret Vercel sends to the cron jobs; without it they all answer 401 |

### Icon system

Icons use `astro-icon` with `@iconify-json/ion` and `@iconify-json/mdi` icon sets. Reference icons as e.g. `ion:diamond-outline` or `mdi:github`.

## Project rules

- **Language**: The site is bilingual. German is the default locale at the root URLs, English lives under `/en/` (Astro `i18n`, `prefixDefaultLocale: false`). Emails and API responses stay German.
- **Adding or changing copy**: Change the German text in `src/data/` and the English counterpart in the matching `*.en.ts` file in the same commit. `getCopy(Astro.currentLocale)` (`src/data/copy.ts`) returns the copy for the current locale; its `Copy` type flags English files that miss an export when you run `tsc`. React islands get their copy as props from the page, they do not import it.
- **Pages**: Each page is implemented once in `src/views/` and rendered by a thin German route in `src/pages/` and an English route in `src/pages/en/`. English slugs that differ (`join`, `contact`, `materials`, `imprint`, `privacy`, `workshops`, `startup-week`) are listed in `src/lib/i18n.ts`. MDX pages (legal, workshops, peer-to-peer) exist once per language.
- **News articles**: German in `src/content/projects/`, English translation in `src/content/projects/en/` under the same file name (collection `projectsEn`). `getNews(locale)` in `src/lib/news.ts` reads both.
- **Language toggle**: `LanguageToggle.astro` sits next to `ThemeToggle` in the header and the mobile nav. `DefaultLayout` derives the target and the hreflang links from the URL; pass `alternatePath` when the counterpart has a different path (`null` = no counterpart).
- **Dark theme**: The site uses a near-black background (`--color-bg`, `hsl(255 10% 5%)` = `#0c0b0e`). New UI should match this palette.
- **Component file type**: Use `.astro` for static/structural components and `.jsx`/`.tsx` for interactive React components that need `client:*` directives.
- **Content changes**: Edit copy in `src/data/staticContent.ts` / `staticContent.en.ts` (nav, footer, hero, FAQ, features) or `src/data/teamsData.ts` — not inside components.
- **Navigation items**: Managed in `src/data/staticContent.ts` under `navigation.menuItems` (supports nested `children` for dropdowns).
- **New content collection**: Add definition to `src/content.config.mjs`, create directory under `src/content/<name>/`, add `.md` files there.
- **Shadcn UI components**: Live in `src/components/ui/`. Use `@/lib/utils` for the `cn()` helper (already present at `src/lib/utils.ts`).
- **Self-updating rule**: After every session where something new is learned about this codebase, append it to this CLAUDE.md under "Project rules".
- **Events outside Luma**: `/events` shows the upcoming and past events of the Luma calendar (`loadEvents(locale, period)`) in `src/lib/luma.ts`, each merged with hand-listed events from `src/data/externalEvents.ts` (English location in `externalEvents.en.ts`, keyed by id). External events link to their own `registerUrl` instead of the Luma embed and move to the past section after `endAt`.
- **Newsletter = WhatsApp**: There is no email newsletter, no double opt-in and no Resend audience. The WhatsApp community is the newsletter. Copy and emails must not promise email updates. The invite link lives once in `src/templates/emails/links.ts` (`WHATSAPP_INVITE_URL`) and is sent by the community invite mail and the application confirmation.
- **Sending mail from API routes**: The Resend SDK returns `{ error }` instead of throwing. Wrap every send in `assertSent()` (`src/lib/resend.ts`). API responses carry fixed German messages, never `error.message`.
- **Contact address**: `stud.initiative.ignite@leuphana.de` is the only current address. It lives in `globalConfig.contactEmail` (`src/data/staticContent.ts`), which the mail routes use as `replyTo`, because the sending domain `info.ignite-startupclub.de` does not receive mail.
- **Social links**: Instagram is `instagram.com/ignite.lueneburg`, LinkedIn is `linkedin.com/company/ignite-leuphana`. The website uses `socialLinks` in `src/data/staticContent.ts` (+ `.en.ts`), emails use `INSTAGRAM_URL` / `LINKEDIN_URL` in `src/templates/emails/links.ts`. Change both together.
- **Luma requests need a User-Agent**: `api.lu.ma` answers 429 to the default User-Agent of Node's `fetch` and curl. `src/lib/luma.ts` sends its own; keep it when changing the request.
- **Links in news articles**: Use Markdown links (`[Text](/mitmachen)`, English `[Text](/en/join)`). A `<link href>` tag renders as plain, unclickable text. Each article's URL is its lowercased file name (`OpenWeekly2026.md` → `/news/openweekly2026`), so a second article on the same topic needs its own file name and image. Covers are cut to 4:3 on the news cards and 16:9 on the article page, so pick a cover near 4:3; put wide group photos inside the text as `![alt](../../assets/optimized-sources/news/<file>)` (one `../` more from `en/`), which shows them uncropped and as WebP.
- **Members area**: `/mitglieder/` and `/en/members/` are only reachable with a session, except the login page. `src/middleware.ts` guards them, sets `Astro.locals.member` ({ email, role }) and lets only admins open admin pages; new member pages go below these paths with `prerender = false` and get their slug per language in `PAGES` (`src/lib/memberAuth.ts`). The login page is a page of its own (`DefaultLayout bare`: no header, footer or header padding), split into the deep purple `surface-brand` panel (purple in both themes, copy in `memberArea.login.panel`) and the `MemberLoginCard` island on the theme background: email plus password (scrypt hash over an HMAC of the password with a pepper derived from `ENCRYPTION_SECRET`, scheme `scrypt-hmac`, so a database dump alone allows no offline guessing; every attempt is reserved atomically in `reserveLoginAttempt` before the check, five failures lock the account for 15 minutes, one error message for every failure). A first or forgotten password is set with a 6-digit code from `/api/members/code`: valid 10 minutes, 5 entries, stored as an HMAC keyed from `ENCRYPTION_SECRET`, at most 5 codes per address and hour. `?reset` opens the card at the code request. Admins add members on `/mitglieder/verwaltung`, which mails an invitation without a token; every change goes to the `member_audit` collection. The first admin needs no database access: while no admin exists, `/api/members/code` makes an address on `INITIAL_ADMIN_HASHES` (`src/lib/initialAdmins.ts`, SHA-256 of the address because the repository is public) an admin before sending the code. With database access `node scripts/members.mjs add <email> --admin` does the same. Owners ("Hauptadmin", `OWNER_HASHES` in the same file, same hash format) are admins whom no other admin can demote or remove: `/api/members/admin` answers 409 `owner` with the neutral message "Diese Änderung ist nicht möglich." The admin page shows owners as plain admins with the usual actions, and the member summaries carry no owner flag, so neither the list nor the page data reveals who is protected. The local `.env` has no valid `RESEND_API_KEY`, so code mails fail locally; store a known code with a script instead. Sessions are stored only as SHA-256 hashes; setting a password or removing a member ends their sessions. Every endpoint under `/api/members/` needs a session (401 from the middleware) unless it is listed in `PUBLIC_API` (`memberAuth.ts`), so new endpoints, for example for internal contacts, are closed by default. All member pages and endpoints get no-store and anti-framing headers from the middleware. More than 30 failed logins per client address in 15 minutes block that client (`reserveClientAttempt`, addresses stored only as HMAC). `/api/members/code` answers no earlier than 1.5 s, so its timing does not reveal members. The JSON endpoints require `Content-Type: application/json`. Form posts and posts without a type from other sites get 403 from `isCrossSiteForm` (`memberAuth.ts`, first step of the middleware, so unlike Astro's own check it also runs in `astro dev`). Astro's `checkOrigin` is off in `astro.config.mjs`, because it has no exceptions and would refuse the OAuth token endpoint in production.
- **Header and ViewTransitions**: `ViewTransitions` (`SiteMeta.astro`) swaps the header on every navigation and module scripts run only once, so header scripts bind element listeners on `astro:page-load` (it also fires on the first load). The pill's hover state is the `data-hovered` attribute, not `:hover`: after a swap `:hover` only returns with the next pointer move, and during the transition the overlay is hit-tested instead of the page. `astro:before-swap` carries hover, highlight and scroll state into the new header.
- **Email signature**: Members build their opt-in Outlook signature on `/mitglieder/signatur` (`/en/members/signature`, `MemberSignaturePage.astro` + `SignatureGenerator.jsx`). The markup comes from `src/lib/emailSignature.ts` (tested): tables with inline styles only, every input escaped. The text inputs are kept as a draft in localStorage under `signatureStorageKey(account)`, one key per account, because members share browsers. Its tables carry `width:auto;table-layout:auto` and the photo `max-width:none` inline, because the site's reset (`table { width: 100%; table-layout: fixed }` in `_reset.scss`, Tailwind's `img { max-width: 100% }`) otherwise stretches the preview and splits photo and text in half. Mail clients do not show SVG, so the logo ships as `public/email/ignite-badge.png`, rendered from `Logo.astro` by `node scripts/email-signature-assets.mjs`. The badge stays public because recipients load it without a session. Copied signatures point images at `https://www.ignite-startupclub.de` (the apex domain redirects to `www`), so a new image only works in pasted signatures after the deploy.
- **Signature photo**: Each member has one photo, used by the signature, the header, the admin list and the task directory. Members upload it in `PhotoCropper.jsx`, on the signature page and in `TeamChoice.jsx`, so both always show the same one. The board never sees the team choice and uses the signature page. The privacy policy calls it a profile photo that other members see. Cropping runs in a modal `<dialog>` without a `<form>`, because both pages sit in a form: inline, the page's own submit button dropped an unfinished crop, and `FormDialog` would nest forms. Chromium fires the dialog's `close` event on the next frame, so in a hidden Browser pane the crop state stays until a screenshot forces one. Removing the photo leaves an empty image in signatures already pasted into Outlook, so the status text tells members to copy theirs again. Members move and zoom it in the browser, and only the cut 192 px circle goes as a PNG data URL with transparent corners to `POST /api/members/photo` (`decodePhoto` checks the PNG signature, the IEND chunk and `PHOTO_MAX_BYTES`, 160 KB, above any uncompressed 192 px PNG; `DELETE` removes it). The circle is in the image itself because several Outlook versions (classic Windows/Mac, Outlook for iOS) drop `border-radius` when they send or reply, which showed photos square; `border-radius` stays in the markup for the photos uploaded before as JPEG, which `/api/signature-photo/<id>` still serves with `photoType`. Those members only get the round photo after uploading again. Photos live in the `member_photos` collection (Mongo `Binary`), at most one per member. Every upload gets a new random id and deletes the old image, but the new document keeps the old ids in `formerIds` (`formerPhotoIds`, tested), so `/api/signature-photo/<id>` answers with the current photo under every id the member ever had: pasted signatures and sent mails keep a working image. It sends the image directly, not as a redirect, and is cached for a day only, because a URL can now change its content. Only `deletePhotos` and removing the member end all links (404). Links replaced before `formerIds` existed stay dead. That route is public on purpose (recipients load it without a session) and sits outside `/api/members/`. `signatureHtml` only shows photos whose id passes `isPhotoId`, never external URLs. The admin list shows the same photo next to each member (`memberSummaries`, one query for all photos). Mail clients cannot be trusted with `object-fit`, which is why the crop happens before upload. Outlook for iOS forces `max-width: 100%` on images, which squeezed the photo to an oval in the narrow column; the photo cell carries `width`/`min-width` and the image `min-width:96px` plus `height:auto`, so it stays a 96 px circle (test in `emailSignature.test.ts`).

Allowed values, parsing and filters live in `src/lib/contacts.ts` (tested), the Mongo access in `src/lib/contactsStore.ts` (collections `crm_contacts` and `alumni`, string UUIDs as `_id`, `database()` from `members.ts`). Unsealed or moved values throw, so the collections hold no plain text, and sorting and search run after decryption in JavaScript. A keyed `emailHash` refuses a second contact with the same address (409 `duplicate`). The email of an alumni profile that takes no requests reaches only admins and its creator, and only they switch `open`.

It offers logos, mark, profile pictures, LinkedIn banner and team icons for download, plus colours, fonts and logo rules. The file list is `brandGroups` in `src/data/brandKit.ts`, the files sit in `public/brand/` (public on purpose, like the email badge), names and texts in `memberArea.branding.assets` keyed by asset id. - **Member text size**: `DefaultLayout` puts `.member-area` on `body` on every members area page with a header (not the login page). The class in `global.css` raises the small steps by 2 px (`text-2xs` 13, `text-xs` 14, `text-caption` 15, `text-sm` 17) and widens `--container-wide` to 90rem; public pages keep 11, 12, 13, 15 px and 80rem. - **Tasks module**: `/mitglieder/aufgaben` (`/en/members/tasks`, `MemberTasksPage.astro` + `TaskWorkspace.jsx` with its parts in `src/components/forms/tasks/`) opens on a hub for every member (`TaskOverview.jsx`: a calendar of this week and the next from Monday (`weekStart`, past days dimmed; the Weekly only shows from today on, because `seriesDates` makes no past dates), one card each for tasks, events and projects). There are no tabs: the cards lead to the pages Kanban-Board, Events and Projekte, each with a link back. The projects card on the hub shows only the open projects the member leads (`ledProjects`, tested); the Projekte page still starts on all teams. A click on an event in either calendar opens its project, or `EventDialog` when it has no plan yet; in the month grid the day's button is a layer behind the title buttons. `_reset.scss` sets `button * { pointer-events: none }`, so a real mouse click on a child of a button reports the button as `e.target`, while `.click()` from `javascript_tool` reports the child; test such clicks with `computer`. It posts to `/api/members/tasks` (action pattern like the CRM, answers with what changed since the `revision` it sends, see "Live updates"). Rules without database access live in `src/lib/tasks.ts` (tested, no extensionless imports so `node --test` can load it), Mongo access in `src/lib/tasksStore.ts`: `task_projects` embeds tasks and the activity log (capped at 300 entries) so one update is atomic; the log stays out of lists and answers and loads when its tab opens (`GET ?activity=<id>`); a unique partial index on `event.id` allows one planning project per calendar event. Members are referenced by the hex `_id` of their `members` document, never by email, so no address reaches the client; the directory sends only id, name and photo. Names come from `firstName`/`lastName` on the member (the island asks once, `displayName` falls back to the address's local part). The calendar uses `loadTaskEvents` (`src/lib/taskEvents.ts`: Luma, `externalEvents` and the Weekly), never a copy; `syncEvents` only refreshes the event snapshot of planning projects and marks events that left a complete calendar as `missing`, it never deletes. Copying a template or an earlier project never takes status, people or absolute dates. - **Single tasks mirror their card**: A single task is a card of type `task` with one task. Title, description and deadline live on card and task (`MIRRORED_FIELDS` in `tasks.ts`), and the server writes both whenever one changes. The islands show such a change on both before the answer through `patchedProject` (tested); `patchedTask` stamps `doneAt` when a task is ticked, so the done column sorts it at once.
- **Keyboard focus in the tasks module**: Rows and cards carry `data-task-item` (the task id), their controls `data-control` (`menu`, `check`), and the list around them `data-focus-scope`. Call `keepFocus` (`taskUi.jsx`) before a change that moves, hides or removes the focused task, and what it returns after the change: it focuses the same control of that task, else of the next one, else of the one before. `focusTask` focuses a task that came back with an undo, and `showRest` moves focus to the first entry that a "+N" or "Alle anzeigen" button reveals, because the button goes away. `checkVisibility()` decides what counts as visible, so tasks in a closed `<details>` are skipped. Escape and every action of `TaskContextMenu` give focus back to the card's button before the action runs, so a panel opened from the menu returns focus to the card.

- **Startup-Woche**: `/startup-woche` (`/en/startup-week`, `StartupWeekPage.astro`) is the link in the Instagram bio for the weekly post "Deine Startup-Woche": external startup events in Lüneburg and Hamburg, each with a direct registration link. A week is one JSON file in `src/content/startupWeek/` named after its Monday (`2026-11-09.json`), with `start`, and per event `date`, optional `time`, `emoji`, `host`, `url` and the texts in `de` and `en` (`title`, `text`, `place`, optional `note`). The schema in `content.config.mjs` runs `editionProblems` (`src/lib/startupWeek.ts`, tested), so a start that is no Monday or a date outside the week fails the build. The page renders per request with an hour of edge cache; `currentEdition` shows the newest week that has begun by tomorrow, so a file added before Sunday shows from Sunday on, and after the last week ended the page shows an empty note. Past days stay dimmed without a button. Check every link before adding it: the Luma link of the first edition's cofounder dating was already dead on 2026-11-09, so it points to the Startup City Hamburg event page.
- **Repeating tasks**: A task (shared or private) has `repeat` (`REPEATS` in `src/lib/tasks.ts`: '', weekly, biweekly, monthly; missing reads as ''), set in the task editor of the project panel and in `PrivateTaskDialog`. `nextTurn` (tested) decides what a change does: a repeating task that gets done, by checkbox, board column or MCP tool, goes straight back to the backlog with `nextDue`, the first step of its rhythm after today counted from its deadline (monthly from the first deadline, so 31 January gives 28 February and then 31 March); without a deadline the rhythm starts today. The activity log gets `taskDone` and `due`, and the toast names the next deadline (`results.repeated`). The card of a single task moves along with it (`MIRRORED_FIELDS`). Templates do not carry `repeat`. `patchedTask` and `patchedProject` need `today` for this. There is no cron: nothing changes until someone finishes the task.
- **Luma import for own events**: An event is always a Luma event, decided by Noah on 2026-11-11: without a Luma event it is a project. The form for an own event (`CreateDialog.jsx`) asks only for the Luma link; „Von Luma importieren“ posts it to `/api/members/luma-import` and the dialog shows a preview of what Luma says. Own events stored before the rule have `luma: null` and keep working. `src/lib/luma.ts` (tested with made-up answers shaped like Luma's, because the repository is public) holds both ways to read Luma: the IGNITE calendar (`calendar/get-items`) and single events by slug (`lumaEventFromUrl`: `api.lu.ma/url?url=<slug>`, falling back to `__NEXT_DATA__` of `luma.com/<slug>`; the page has no JSON-LD). Both describe an event in one shape, mapped by `mapEvent`. This reads private events of other Luma accounts too (`visibility: private`, checked 2026-11-11 with the Utopia-Dinner), which no calendar list shows. `src/lib/lumaLink.ts` (tested) accepts only `lu.ma`/`luma.com` with or without `www`, no port or credentials, one path segment; only the slug leaves it and the server builds every request URL itself with `redirect: 'error'`, against SSRF. When Luma hides the address until registration (`geo_address_info.mode: obfuscated`) or the event is online, `hidden` names the field and the form asks to fill it in by hand. An own event stores `luma: { id, url }` (null for events by hand), `coverUrl` (only `*.lumacdn.com`), `endTime` and `endDue` ('' = ends on its day); a unique partial index on `luma.id` refuses a second import (409 `duplicate`), and the import answer names an existing one (`existing`) or the IGNITE calendar entry to plan instead (`listed`). `fitsItsKind` refuses these four fields on plannings and other project types.

- **Error log**: Vercel keeps runtime logs only briefly on Hobby, so server code calls `logError(context, err)` (`src/lib/errorLog.ts`) instead of `console.error` in its catch blocks. It still writes to the runtime log and also stores the entry in `error_log` (TTL 30 days): context, error type, message and the top 8 stack frames, with email addresses replaced (`errorEntry` in `src/lib/errorReport.ts`, tested) and no member or request data. `logError` never throws. The middleware wraps every request and logs what no route caught, under `context.routePattern`, not the path, because paths like `/api/calendar/<token>.ics` carry secrets. `/api/cron/error-report` runs at 06:00 UTC and mails the unreported entries, grouped (`errorGroups`, at most 20 groups), to the admins whose `members.errorMails` is true. Each admin switches this for themselves under "Nur für dich" on the page "Systemzustand" (`PERSONAL_DEFAULTS` in `settings.ts`, off by default; the settings endpoint takes either global or personal switches, never both). Without new entries no mail goes out; without recipients the entries count as handled, so switching on later sends no backlog; a failed send keeps them for the next run. Demoting an admin removes `errorMails`. `luma.ts` and `members.ts` keep `console.error`: `luma.ts` must stay importable by `node --test`, and `members.ts` is imported by `errorLog.ts`. A database outage cannot reach the log or the recipients; it only shows in the runtime log. The page "Systemzustand" (`/mitglieder/verwaltung/system`, `/en/members/admin/system`, `MemberSystemPage.astro` + `ErrorBoard.jsx`, admins only through `isAdminPath`, linked in the profile menu and on the member management page) shows the entries of 24 hours, 7 or 30 days (`?tage=`, `errorPeriod`) grouped and newest first, the counts, a database ping, region and commit from Vercel's system variables and the last report run. "Als erledigt markieren" (`/api/members/errors`) stores the `groupKey` in `error_resolved` (TTL 60 days); a later entry of that group shows it as "Wieder aufgetreten" (`groupStatus`), with no reset needed. The mail's button links there. The switch component lives in `memberUi.jsx`.
